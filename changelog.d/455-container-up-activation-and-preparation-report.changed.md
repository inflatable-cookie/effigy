`container up` activation and preparation report their own state instead of a fixed label. Compose's whole-stack step moves to the restart-policy read once Compose returns, and a shared service's step does the same, so a stalled `restart: unless-stopped` read never shows a finished Compose call. The creation-time policy load names the preparation stage now running (checkout identity, declaration with ports and loopback, render inputs, the second declaration resolution that follows them, render, mount sources), and environment activation draws only the transition's own live step instead of a second fixed one. A declared `[containers.<NAME>.health]` check that answers a definite status outside `2xx`/`3xx` is refused at once with the status it observed and the primary container's last output, instead of spending the whole health budget on an answer waiting cannot change (effigy#455). Only a complete status line counts as that answer: the probe reads one bounded line across partial reads, so a split response or a peer that closes after a prefix keeps the budgeted wait instead of reporting readiness or a mismatch it never observed. That container is the identity the runtime's own row reports for the service, so an explicit Compose `container_name` reads its own logs and is the one the diagnostic and `waiting_on` name. That identity is carried from the readiness probe's own observation, so naming it costs no extra runtime read; a wait that observed no services reads it once, under a live step naming the runtime row it waits on; the failed container's log tail is read under its own named step too, and a log read the runtime does not answer is reported as unavailable. When the runtime cannot name a container, the diagnostic describes the environment and its primary service instead of calling the environment a container. The restart-policy apply that follows Compose names its own stages — the Compose declaration read, the runtime inventory read, then the update — for the whole stack and for each shared service, so a stalled read never claims an update was sent.
