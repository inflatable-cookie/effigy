`EFFIGY_STRICT_PERSISTENCE=1` opts a process into a run that prepares nothing: no store creation, schema `ALTER`/backfill, expired-row prune or checkpoint (at `COMMIT` or at the last connection's close), and no maintenance either — checkpoint, vacuum, retention pass, machine compaction and the explicit repair all refuse or do nothing under the switch, and even observing the write-ahead log no longer checkpoints it. A journal that is not already prepared, or that needs recovery (a rollback journal, a torn log, or a log whose wal-index is missing), is refused **before the admission hook runs**, with a typed refusal naming `effigy run prepare` — the new step that prepares a checkout journal outside a strict run, with `--check` to verify that nothing would be written — and a refused open leaves the store's bytes untouched. Contract 049 now states the strict route's complete physical contribution with file:line: 0 bytes of main database, one 32 KiB wal-index page, one row of at most 960 stored bytes, and a write-ahead log of `32 + 32 × (page size + 24)` = 131,872 bytes as an operating budget that every strict run measures and verifies (the write appends 3 frames in every tested state), because SQLite's own balance and cache-spill behaviour means no a-priori maximum can be claimed honestly. Behaviour without the switch is unchanged (effigy#981).
