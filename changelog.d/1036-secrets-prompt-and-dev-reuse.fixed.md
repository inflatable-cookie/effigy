A passphrase prompt is no longer hidden under a running progress display, and a resolution whose container keys are all optional no longer waits on one: `effigy workspace` on a healthy stack could sit at "Updating containers" for minutes while an invisible prompt waited on a passphrase nobody knew to type. The prompt now clears the step lines, shows the question, and resumes the steps afterwards, in every prompt Effigy reads (container and task secrets, `secrets` commands, Rhai secrets); inside a managed pane, whose output is captured, Effigy refuses to prompt and names `effigy secrets unlock` instead. When this machine holds a local-dev key but the run is not an `effigy dev` session, the undelivered-key warning now says exactly that — "the local-dev key only unlocks `effigy dev`, and this run is not a dev session; for direct commands run `effigy secrets unlock` once at a terminal" — instead of claiming a locked vault, and the previous message stays for a genuinely locked vault with no key. Every prompt now obeys the same pane rule — container and task secrets, the local-dev upgrade, `effigy secrets` prompts and Rhai secret access — so no path can ask a question into a captured pane, and a value read for `effigy secrets set` never becomes the session's vault passphrase. A dev session that reuses an environment a direct `container up` started now delivers the keys it resolves: the task apply writes `runtime.env`/`runtime.json` once the primary service is verified, and reports the keys it changed in that apply — once, naming them and never a value, with the remedy for a service that reads the files only at startup (stop the stack and run `effigy dev` again). Nothing is carried between applies: an apply that writes what the service already holds says nothing. The local-dev key's command scope is unchanged (effigy#1036).
