**A workspace session's custody can live in a detached process.** A serving host supervisor starts before the session run is adopted or the listener exists, performs the activation in its own process, announces the committed session over the kernel's bounded engine-event channel, and then keeps that same run, listener, key, grant book and admitted clients while it serves and settles exactly once. The initiating command only launches it and reads the result: an absent acknowledgement is an error, an unacknowledged detach is the kernel's owner-loss path, and no dropped local owner is reported as success. The container-up producer stays #452's (`ContainerUp` refuses by name in this head); the process-lifetime proof runs the same launcher with the disposable activation the `workspace-serving-fixture` feature compiles in, so it proves process custody and not container-mode preparation. One session serves through one owner: a second launch for a session whose listener is already live refuses at the kernel boundary, and the claim is released only when that launch stops or settles. An unacknowledged detach is the kernel's owner-loss path, which stops serving and settles instead of claiming the session.
