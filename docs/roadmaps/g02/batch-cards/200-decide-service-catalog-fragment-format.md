## Objective

Settle the fragment template format, parameter schema, dependency model, volume
declarations, and conditional handling so that implementation can begin on the
catalog crate.

## In Scope

- template syntax decision
- `service.toml` schema
- how fragments reference other services in the stack
- how fragments declare volumes
- how conditional sections work
- one complete example fragment to prove the format

## Out Of Scope

- implementation
- CLI integration
- manifest schema for service declarations (settled in architecture doc,
  refined during implementation)

## Decisions

### 1. Template Engine: Minijinja (Jinja2 syntax)

Simple `{{var}}` substitution is insufficient — fragments need conditionals
(does this service depend on a database?) and loops (list of PHP extensions).
Rather than inventing a custom syntax, use an existing lightweight engine.

**Minijinja** (`minijinja` crate):

- Jinja2 syntax: `{{ var }}`, `{% if cond %}`, `{% for x in list %}`
- Small dependency footprint (author of serde, well-maintained)
- Good error messages with source locations
- Filters: `{{ list | join(" ") }}`, `{{ var | default("fallback") }}`

Why not Tera: heavier dependency, more features than needed. Why not
handlebars-rs: less intuitive conditional syntax, Rust-specific quirks.

Why not `${VAR}` syntax: conflicts with Docker Compose's own variable
interpolation. Compose would try to expand `${VAR}` before effigy gets to it.

### 2. Template Context

The assembly engine passes a context object to each fragment:

```
{
  // Fragment's own parameters (from manifest service declaration)
  "version": "8.3",
  "extensions": ["pdo_mysql", "gd", "redis"],
  "document_root": "public",
  "working_dir": "/var/www/html",

  // Service identity (assigned by assembly engine)
  "service_name": "app",

  // Other services in the stack (for depends_on, networking)
  "services": {
    "db": { "name": "db", "catalog": "mariadb", "port": 3306 },
    "cache": { "name": "cache", "catalog": "redis", "port": 6379 }
  },

  // System variables
  "repo_root": ".",
  "catalog_path": "<resolved path to fragment directory>",
  "project_name": "client-x-dev",

  // Volume names (generated by assembly engine, prefixed with project)
  "volumes": {
    "data": "client-x-dev-mariadb-data"
  }
}
```

This means fragments can reference other services without hard-coding names:

```yaml
{% if services.db %}
    depends_on:
      {{ services.db.name }}:
        condition: service_started
{% endif %}
```

### 3. service.toml Schema

```toml
[service]
name = "php-fpm"
description = "PHP-FPM application server"

[params.version]
type = "string"
default = "8.3"
description = "PHP version"

[params.extensions]
type = "list"
default = []
description = "PHP extensions to install via docker-php-ext-install and pecl"

[params.document_root]
type = "string"
default = "public"
description = "Document root relative to repo root"

[params.working_dir]
type = "string"
default = "/var/www/html"
description = "Container-side working directory for the repo"

[capabilities]
exec_target = true
shell = "/bin/bash"

[volumes.data]
mount = "/var/lib/mysql"
named = true
persist = true
description = "Database storage"

[ports]
default = [9000]
description = "FastCGI port (typically not exposed to host)"

[depends_on]
# Which catalog service types this fragment can reference
# Assembly engine populates services.X in the template context
# only for services that are actually in the stack
optional = ["mariadb", "postgres", "redis", "memcached"]
```

Parameter types:

- `string` — scalar value, substituted directly
- `list` — array of strings, available for `{% for %}` and `| join()`
- `bool` — true/false, available for `{% if %}`
- `integer` — numeric, substituted directly

Validation rules:

- required params have no `default` — assembly fails if not provided
- type mismatch fails at assembly time with clear error
- unknown params (not in service.toml) are warned but not fatal

### 4. Fragment File Structure

```
<service-name>/
  service.toml                  # parameter schema (required)
  compose.fragment.yml          # compose service template (required)
  Dockerfile                    # build image (optional)
  configs/                      # named config variants (optional)
    default.conf
    laravel.conf
    ...
```

When `Dockerfile` exists, the compose fragment should reference it via
`build.dockerfile`. When it doesn't, the fragment uses a pre-built `image`.

Config variants are selected by a `variant` or `config` parameter. If neither
is specified, `default.conf` is used (if the configs directory exists).

### 5. Compose Assembly Output

The assembly engine produces a single compose file with:

- `services:` — one entry per declared service, rendered from fragments
- `volumes:` — top-level named volumes for all `named = true` volumes
- `networks:` — one default network shared by all services
- no `version:` key (modern Docker Compose doesn't need it)

Override support: if `infra/dev/compose.override.yml` exists, Docker Compose
merges it via `-f generated.yml -f override.yml`.

### 6. Complete Example: php-fpm Fragment

**service.toml:**

```toml
[service]
name = "php-fpm"
description = "PHP-FPM application server"

[params.version]
type = "string"
default = "8.3"
description = "PHP version"

[params.extensions]
type = "list"
default = []
description = "PHP extensions to install"

[params.document_root]
type = "string"
default = "public"
description = "Document root relative to repo root"

[params.working_dir]
type = "string"
default = "/var/www/html"
description = "Container working directory for repo mount"

[capabilities]
exec_target = true
shell = "/bin/bash"

[depends_on]
optional = ["mariadb", "postgres", "redis", "memcached"]
```

**compose.fragment.yml:**

```yaml
services:
  {{ service_name }}:
    build:
      context: {{ repo_root }}
      dockerfile: {{ catalog_path }}/Dockerfile
      args:
        PHP_VERSION: "{{ version }}"
{% if extensions %}
        EXTENSIONS: "{{ extensions | join(' ') }}"
{% endif %}
    volumes:
      - {{ repo_root }}:{{ working_dir }}
    working_dir: {{ working_dir }}
    environment:
      DOCUMENT_ROOT: "{{ document_root }}"
{% if services.db %}
    depends_on:
      {{ services.db.name }}:
        condition: service_started
{% endif %}
{% if services.cache %}
      {{ services.cache.name }}:
        condition: service_started
{% endif %}
```

**Dockerfile:**

```dockerfile
ARG PHP_VERSION=8.3
FROM php:${PHP_VERSION}-fpm

ARG EXTENSIONS=""

RUN if [ -n "$EXTENSIONS" ]; then \
      apt-get update && apt-get install -y --no-install-recommends \
        libpng-dev libjpeg-dev libfreetype6-dev libzip-dev \
        libmemcached-dev zlib1g-dev libicu-dev && \
      docker-php-ext-configure gd --with-freetype --with-jpeg && \
      for ext in $EXTENSIONS; do \
        case "$ext" in \
          redis|memcached|xdebug) pecl install "$ext" && docker-php-ext-enable "$ext" ;; \
          gd) docker-php-ext-install gd ;; \
          *) docker-php-ext-install "$ext" ;; \
        esac; \
      done && \
      apt-get clean && rm -rf /var/lib/apt/lists/*; \
    fi

WORKDIR /var/www/html
```

### 7. Config Variant Selection

For fragments with a `configs/` directory (like nginx):

- `variant = "laravel"` → uses `configs/laravel.conf`
- `config = "infra/nginx.conf"` → uses project-local file (overrides variant)
- neither specified → uses `configs/default.conf` if it exists

The assembly engine mounts the selected config into the container at the
appropriate path (declared in the fragment's compose template).
