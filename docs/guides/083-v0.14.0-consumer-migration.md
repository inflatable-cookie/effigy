# 083 - v0.14.0 Consumer Migration

This checklist is for consumers moving from the published v0.13.1 baseline to
the published v0.14.0. The v0.14.0 gateway path is blocked for pre-identity
upgrades; see the gateway section below. The [release contract](../knowledge/contracts/release.md)
owns release authorization and evidence; the linked contracts own the behavior
described below.

## Breaking changes

| If you rely on… | Before upgrading |
| --- | --- |
| `effigy admission status`, `run`, or `runs`, or the Effigy-owned admission store | Move admission monitoring and run reconciliation to Queue/Nucleus. Effigy no longer has those commands or reads `EFFIGY_ADMISSION_DIR`; old default or custom files stay untouched and opaque. Do not delete or migrate them as part of an Effigy upgrade. The `48183cf` binary in contract 049 is local rollout evidence, not a published consumer rollback target. See [host-wide validation](080-host-wide-validation-admission.md) and [contract 049](../knowledge/contracts/049-heavy-validation-admission-contract.md). |
| `EFFIGY_HOST_SCHEDULER=0` to run heavy work locally | Remove that setting. Unset or `1` uses Queue/Nucleus; `0` and malformed values fail closed before task effects. There is no automatic local fallback. A deliberate operator override requires `EFFIGY_SCHEDULER_OVERRIDE` with a reason. |
| Rhai `storage::*` calls (`provider`, `status`, `ls`, `head`, `get`, `put`, `delete`) | Remove or replace each caller with an integration owned by the consumer. Removed calls fail with an unknown-function error and have no compatibility shim. Effigy leaves existing objects, buckets, secrets, generic MinIO services, and independent consumer adapters alone. See [contract 043](../knowledge/contracts/043-feature-placement-and-surface-migration-contract.md). |
| A settings-only `.paseo/queue.json` | Move supported repository overrides to Queue's per-repository settings with `repository.set`; use `repository.get` or `repositories` to inspect them. The operator CLI/API accepts an absolute existing checkout path or normalized `owner/name` origin. The current settings row supports `closeout`, `validation`, `reviewer`, `qa`, `validationPolicy`, and `note`; `closeout` applies only when no control manifest governs the repository. `repository.set` patches named fields, and `null` clears a nullable setting. Project membership uses `project.get` with a key or structured `{repository:{origin,path}}`, and `project.upsert` for grouping. The former settings-shaped `project.set` and string-shaped `project.get` calls are rejected. Keep a `.paseo/queue.json` that still declares Queue hooks; remove only an obsolete settings-only file. Queue closeout is the default when no control manifest applies, and `effigy init northstar` no longer creates the file. See the [Northstar consumer contract](056-northstar-effigy-consumer-repo-contract.md), [Queue Spec 022](https://github.com/inflatable-cookie/paseo-northstar-queue/blob/main/docs/knowledge/specs/022-queue-projects-without-manifests.md), and the [Queue RPC schema](https://github.com/inflatable-cookie/paseo-northstar-queue/blob/main/shared/contracts.ts). |
| `effigy papercuts` or its JSON schemas | Move active papercut records and capture to Queue's papercuts table. The Effigy command, schemas, crate, and starter file are removed; see the [Northstar consumer contract](056-northstar-effigy-consumer-repo-contract.md). |
| The default `effigy docs` log-index or distribution-closeout path `docs/logs/` | Update consumers that inspect generated output to use `docs/notes/`, or pass an explicit path if the repository intentionally retains the former layout. |

## Heavy work and environment values

The built-in `qa`, `ci`, and `ci:fresh` selectors are heavy by default. Tasks
and drafts may also declare `admission = "heavy"`; a QA group with a heavy
member is submitted as one scheduler run. Before upgrading, ensure the
Queue/Nucleus host-run scheduler is available wherever these selectors run.
An unavailable or untrusted scheduler fails heavy work with exit 75 rather
than running it locally. See [contract 049](../knowledge/contracts/049-heavy-validation-admission-contract.md)
and [guide 080](080-host-wide-validation-admission.md).

Heavy submissions now carry only reviewed runtime controls and environment
names explicitly referenced by the selected task or its transitively composed
tasks and drafts. For a QA group, Effigy unions those names across resolved
members. Ambient credentials and unrelated shell variables are excluded, while
a required secret can still be passed when its name is declared by the task's
existing environment configuration. Explicitly named process profiles retain
their process-environment fallback; catalog-defined and qualified profiles
resolve their environment from manifests. Check each heavy task for undeclared
values it previously inherited implicitly.

## QA-group controls and interrupted runs

QA groups and their versioned plan, run, and status payloads are available.
`qa-group stop` and `hard_timeout_ms` are still unsupported; definitions that
request `hard_timeout_ms` are refused before running. A run whose owner is lost
or whose result cannot be proved is `unknown`, never a pass; a handled
interrupt is recorded as cancellation. Use the supported group status surface
and Queue/Nucleus reconciliation; do not infer completion from missing logs or
a dead owner. See [guide 081](081-bounded-qa-groups-workflow.md),
[guide 082](082-owned-run-supervision-workflow.md),
[contract 051](../knowledge/contracts/051-bounded-qa-groups-contract.md), and
[contract 052](../knowledge/contracts/052-owned-run-supervision-contract.md).

## Container and worktree behavior

Plain primary-service `effigy exec` now requires that service to be running. If
it is stopped, start it explicitly with the suggested `effigy container up`
command; plain `exec` does not start the VM, service, or gateway. Routed tasks
and `effigy dev` keep their declared activation lifecycle. See
[guide 063](063-container-system-guide.md).

Linked worktrees receive distinct generated Compose identities automatically.
A full clone is isolated only when its local Git config marks it
`effigy.runtimeScope = ephemeral`. Inspect the resolved scope with
`effigy container scope --json` and its effective host map with
`effigy container hosts`; wire those names into consumer URLs and selectors as
needed. Retire only resources owned by the intended runtime scope with
`effigy container retire`. The [runtime contract](../knowledge/contracts/005-container-runtime-contract.md)
defines identity, route ownership, and retirement boundaries.

Retirement does not accept a container environment name: `effigy container
<NAME> retire` now refuses before lookup or mutation, even with `--scope` or
`--yes`. Partial retirement by environment name is unsupported because one
scope record covers all its environments. Retire the current checkout scope
with `effigy container retire`, or an exact recorded scope after checkout
removal with `effigy container retire --scope <TOKEN>`.

Keep intentional nested host binds in place. Workspace ownership preparation
checks nested mounts at the resolved numeric uid/gid and avoids recursive
chown of host sources, siblings, and shared caches. Isolate a writable Cargo
target separately when the bound host path is not writable; see the workspace
section of [guide 063](063-container-system-guide.md).

## Gateway process identity (published v0.14.0 and unreleased main)

Status: the published v0.14.0 binary is fail-closed and blocks a live
numeric-only record, and it also rejects the operator-owned gateway directory
during elevation, so it cannot complete a legacy upgrade. Corrected main
reports `LegacyIdentityRequired`, accepts the authenticated operator-owned
directory, and provides `effigy gateway recover`. Public channels are currently
pinned to the last good v0.13.1 (GitHub `latest`, Homebrew formula); existing
v0.14.0 installs and explicit v0.14.0 downloads are not protected by those pins.
Install a corrected release, then from an interactive terminal run
`effigy gateway recover --adopt-candidate` for a live daemon, or
`effigy gateway recover --yes` only when the recorded PID is already gone.
`--yes` cannot adopt a live candidate. See
[architecture 034](../knowledge/architecture/034-gateway-legacy-upgrade-recovery.md).

The identity sidecar is present in main `4201e0b3`. The `v0.14.0` tag is
published; the remaining Q-001 assurance governs re-pinning `latest` and the
Homebrew formula to a corrected release, not a re-tag of `v0.14.0`.
`gateway.pid`
stays decimal for compatibility. New starts also publish `gateway.identity`,
a versioned sidecar with the PID, boot identity, and precise process start
identity. Linux records boot ID plus `/proc/<pid>/stat` start ticks. macOS
records `proc_pidinfo(PROC_PIDTBSDINFO)` start seconds and microseconds. Root
writers assign both private record files to the owner of the gateway directory
so the unelevated operator can read them. On unreleased main (task 113; not in
the published v0.14.0 binary), an elevated root caller accepts an operator-owned
gateway directory only for the authenticated operator UID (non-root, matching
ambient `SUDO_UID` when present, with forwarded `HOME` equal to that UID's
passwd home); unauthenticated root still accepts only root ownership.

Status, start, stop, and elevation require the persisted generation to match
the live process. A readable mismatch means that recorded generation is gone;
the current PID is never signalled. Missing, malformed, unreadable, legacy
numeric-only, or unknown identity preserves the records and refuses signalling
or replacement. A matching generation is rechecked immediately before TERM
and KILL. The final identity check and signal syscall still have a TOCTOU gap;
the implementation does not claim atomic PID-reuse protection.

On macOS, if the ordinary operator cannot read a privileged process's live
identity, Effigy may use the bounded read-only `__gateway-identity` command
through its existing administrator prompt. It is limited to the trusted
recorded gateway target and returns bounded identity state. Declined,
unavailable, timed-out, malformed, or non-interactive authentication is Unknown,
so lifecycle commands refuse to act. The reader does not signal, change files,
or start a daemon. The platform API is supported by `proc_pidinfo` and
`proc_bsdinfo`; cross-UID integration against a live elevated daemon was not
run under the task's no-live-operations boundary.

For a pre-identity numeric-only record, Effigy reports a legacy identity
migration requirement. This differs from an unavailable or ambiguous process
probe, which remains an unknown-state error. Version-only, malformed, or
symlink `gateway.version` state is also unknown: `status`, `up`, `down`, and
managed or container auto-start refuse and preserve the files. Both cases
preserve their files and refuse signaling or replacement. A listener or a
numeric PID alone does not prove process ownership, and `up` or `down` is not
a way to bypass this refusal.

The old executable may already have been replaced by the v0.14.0 install, so
do not assume that the previous binary is available at its old path. Even a
preserved v0.13.1 executable uses PID-only lifecycle control; its presence
alone does not make signaling the recorded number safe. `effigy gateway recover`
does not execute a previous binary. A live daemon is stopped only after
elevated role/owner/boot/start/path evidence and explicit digest consent.
Live role evidence is not historical spawn proof; the last identity-check-to-
signal interval remains a TOCTOU. If recover refuses, leave the records
untouched. A rollback to v0.13.1 ignores `gateway.identity` and restores the
old PID-only risk; safe downgrade is not claimed. See the exact policy in
[architecture 020](../knowledge/architecture/020-container-infrastructure-design.md#gateway-process-identity),
[architecture 034](../knowledge/architecture/034-gateway-legacy-upgrade-recovery.md),
and the preserved Q-001/Q-002 rulings in
[questions](../knowledge/questions.md#q-001--gateway-pid-identity).

An unavailable or ambiguous live process probe is also Unknown: status reports
an error, lifecycle commands refuse, and PID/version records stay unchanged.
Do not treat that state as stopped or remove records to retry `up`; resolve the
probe condition and retry. There is no manual PID-based recovery.

## Additive Rhai file publication

Scripts that must publish a complete payload only when a destination is absent
can use `fs::write_file_if_absent(path, contents)`. It atomically exposes the
completed payload and never replaces an existing destination. It is not a
durability guarantee and filesystems without hard-link support return an error
instead of falling back to a partial write.

Existing `fs::copy_if_missing(source, destination)` calls also publish a
complete independent copy with atomic no-clobber behavior. `true` means this
call published its copy; `false` means the destination was already occupied,
including by a concurrent winner or dangling symlink. Occupancy is checked
before opening the source, so an occupied destination returns `false` even if
the source is missing or unreadable. A missing or unreadable source when the
destination is absent, or a filesystem without hard-link support, remains an
error with no overwriting fallback. Review callers that expect last-writer
replacement or assume `true` means a particular source always won; use
`fs::copy` only when replacement is intended. No change is needed for scripts
that do not depend on those race outcomes. See the [Rhai guide](061-rhai-script-steps-guide.md)
and [contract 050](../knowledge/contracts/050-rhai-fs-atomic-publish-contract.md).

## Skill and distribution updates

Plain `effigy init` no longer creates, downloads, refreshes, or installs a
project-local Effigy skill snapshot. If an agent workflow relied on that side
effect, install or refresh the shared Effigy skill through its supported
installation path, or deliberately opt into `skill.codex_project`. Confirm the
agent loaded the intended skill and check the executable on `PATH` separately.
See [guide 047](047-agent-and-cross-repo-adoption.md) and the
[Effigy skill](../../skills/effigy/SKILL.md).

The release matrix contains macOS arm64/x86_64 and Linux arm64/x86_64 assets.
The two macOS SHA-256 sidecars are unsigned checksums, not artifact signatures.
The local checksum fixture verifies its helper and asset selection, not the
four platform builds or hosted publication. Exact-candidate hosted gates and
post-publish verification remain required by the
[distribution protocol](049-ci-binary-distribution-and-release-protocol.md).
The source checkout pins Rust 1.97.1 as its current build toolchain; workspace
manifests do not declare `rust-version`, and CI does not establish a lower
toolchain compatibility range. The checksum fixture also does not prove the
release binaries' target or feature builds.
