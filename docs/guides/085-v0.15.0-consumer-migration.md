# 085 - v0.15.0 Consumer Migration

This checklist is for consumers moving from v0.14.1 to v0.15.0. Most projects
need no manifest change. Check the catalog pack first, then the rows below that
match what your project uses. The [release contract](../knowledge/contracts/release.md)
owns release authorization; the linked contracts own the behavior described here.

## Before upgrading: the service catalog pack

If `effigy service pack status` shows an active installed pack, it must admit
Effigy 0.15. The published pack compatibility ranges are:

- v1.0.1: `>=0.12, <0.13`
- v1.1.0/v1.1.1: `>=0.13, <0.14`
- v1.1.2: `>=0.13, <0.15`
- v1.2.0 (the compiled baseline in Effigy 0.15.0): `>=0.13, <0.16`

No release through v1.1.2 admits Effigy 0.15. Consumers pinning a pack must
move to v1.2.0 or a later pack that admits their Effigy version. Incompatible
installed packs fall back to the compiled catalog under 0.15.0, and workspace
container handoff refuses that fallback.

1. Run `effigy service pack status`.
2. If the active pack does not admit 0.15, run `effigy service pack update`
   to select v1.2.0 or a later pack that admits your Effigy version on `stable`.
   It can be updated from v0.14.1 before upgrading, or from 0.15.0 afterwards.
3. With no active installed pack on the host, the host uses its compiled
   catalog. Any existing guest pack selection is left untouched.

When the host has an active installed pack, the workspace's own pack
(inside the container) is checked against the host's pack during handoff.
An empty guest receives the host's verified pack. A guest
with a different or unknown selection is preserved and refused: inspect it with
`effigy service pack status` as the workspace user. With no active host pack,
the host uses its compiled catalog; the guest selection is neither inspected
nor changed, so an existing guest pack can remain active.

## Removed surfaces

- Replace `effigy watch` with your tool's native watch option or explicit task runs.
- Replace `effigy tasks migrate` with explicit task and test-suite definitions;
  inspect `effigy config` for examples.
- Unset `EFFIGY_MANAGED_STREAM` and use `--headless`. A set variable now errors
  before managed children launch, including with `--headless` already present.
- Remove `[manifest].root`; it now reports a source-specific error.
- Move fragments from `~/.effigy/catalog/` to each repository's
  `infra/dev/catalog/`. The old directory is ignored with a warning and preserved.
- `effigy gateway recover` is retired. v0.14.1 identity-bearing gateway upgrades
  retain `gateway up`/`down`. Pre-0.14 numeric-only state requires administrator
  migration as described in [architecture 034](../knowledge/architecture/034-gateway-legacy-upgrade-recovery.md).
- Run docs QA selectors directly instead of `docs qualified`. The private
  assurance recipe and build profile are removed.
- Listener transition receipts are no longer read or written; existing files
  stay untouched. Current listener state and diagnostics remain available.

Delete `identity`, `unlock` and `external` declarations under `[secrets.vault]`.
They are retired after consumer cleanup; the error names the file and line.
These keys only restated the passphrase default. Vault paths, stored values
and runtime unlocks keep their existing behavior.

## Behavior changes

| If you rely on… | What changes |
| --- | --- |
| `deploy apply` or `deploy redeploy` | Both refuse as not yet supported, including with `--yes`, and name the unexecuted obligations. Model/export and environment configuration stay compatible; old reports remain readable. Use model/export while full execution is designed in the deploy lane. See [guide 074](074-deployment-guide.md). |
| Detached stacks (`startup = "detached"`, e.g. the DecodeLabs bundle) | Before `effigy container up --detach` reactivates a running stack, every container in the Compose project that the up can start or recreate must be proven owned by this checkout, running or stopped. Stopped declared siblings must carry this checkout's checkout and scope labels; an unlabelled stopped container is not proven and Effigy refuses. The pre-label bind-mount exception in the next row applies only to running containers with verified identity in an unscoped checkout. Editing the manifest of a running stack and running `up --detach` applies the change. A *partial* activation (one that failed after Compose started) still refuses changed inputs until `effigy container down`. See [contract 005](../knowledge/contracts/005-container-runtime-contract.md). |
| Direct `compose_file` containers | Effigy now labels them with checkout and scope identity through a Compose override. An existing unlabelled container created by v0.14.1 is adopted only with positive evidence: it passes full identity validation (Compose project, service, and runtime identity) and has a bind mount of this checkout at the policy working directory. Without that evidence, Effigy refuses rather than adopting. Labeled containers must match the checkout and scope identity; a matching `working_dir` alone is insufficient in a scoped checkout. If ownership cannot be proven, verify the stack belongs to this checkout, then run `effigy container down` followed by `effigy container up --detach` to recreate it. |
| Container tasks run under a Queue/Nucleus host run | A direct-command task bound to a container now runs through mapped container exec from the host (`sh -lc`), instead of re-entering Effigy inside the container. `{repo}` and `{project}` render as container-mapped paths. Plain `effigy <task>` from a terminal is unchanged. See [guide 080](080-host-wide-validation-admission.md). |
| Linux workspace Effigy artifacts | An artifact is reused only when its identity matches the host binary and target. A stale one is rebuilt or downloaded, or the handoff refuses with the exact rebuild command. Release binaries download the matching Linux release asset. |
| `[containers.*.host_processes]` names | Names with surrounding whitespace, or two names that collide after upper-casing and replacing punctuation with `_`, are now rejected; they name dependency environment variables. |
| A container named `ports` | `effigy container ports …` is now the machine-wide port registry. A container with that name can no longer be addressed as `container ports <action>`; rename it. |
| Managed host listener routes | Without `EFFIGY_GATEWAY_PRIVATE_STATE_ROOT` they publish to the shared operator gateway. By default, a linked worktree or marked ephemeral clone gets a scoped apex (`api.acme-w<key>.test`), as container DNS routes already did. The primary checkout and checkouts with explicit `share_runtime_identity = true` retain the declared route name. |
| `effigy tasks status` and its JSON | Status is the run journal plus the task's gate: `effigy.tasks-status.v2` / `effigy.tasks-status-all.v2`. A long run reads `running` for as long as it lives; a run whose owner died reads `interrupted` with the settling command. Nothing is written under `.effigy/reports/tasks/` or `.effigy/runtime/tasks/` any more; a task's v0.14 record shows read-only until it first runs. See [contract 018](../knowledge/contracts/018-task-status-query-surface-and-read-model-contract.md). |
| Task locks and `effigy tasks unlock` | Every spelling of a task shares one lock, held exactly while its run lives and released when it exits, `kill -9` included. `effigy tasks unlock` is removed (it refuses with the explanation); remove any "run unlock when stuck" step. A lock conflict exits 75 and names the holder. Old `.effigy/locks/` files are ignored and can be deleted once no v0.14 run is live. |
| Flags after the task name | Effigy's flags go before the task: `effigy --lock-wait-ms 600000 build`, `effigy --plan build`. After the task name, `--plan` and `--json` still work for this release with a note; `--repo`, `--lock-wait-ms`, `--env-schema` and `--verbose-root` now reach the task, with a note. Check scripts and CI lines that pass them after the task. |
| Running from inside a member catalog | A subdirectory run resolves to the root that declares the catalog in `[catalog.members]`, however deep, instead of treating the nearest catalog as its own root. |
| Background processes started by a task | A plain host task's whole process group is stopped when the task ends. Start daemons with their own session (`setsid`, `docker compose up -d`), not `cmd &`. |
| `tasks.<name>.cache` and `effigy tasks cache` | Removed. A task that still declares `cache` is refused with the fix: delete the table. |
| `effigy container shell --bounded` | Discovery adds one small ownership listing to the preparation captures and budgets, and every effect targets the verified container. |

## New, opt-in

- `data_from` on `[containers.<env>]`: borrow another environment's service
  data volumes, so a container environment and its bundle-hybrid twin see one
  database and one bucket per checkout and switching between them hands the
  data over automatically. See [guide 063](063-container-system-guide.md).
- `effigy container ports status|reclaim`: port-registry capacity and safe
  reclamation. See [guide 063](063-container-system-guide.md).
- `effigy container <NAME> shell --command … --bounded`: deadline- and
  byte-bounded finite commands with the `effigy.container.bounded-exec.v1`
  payload.
- Submit a heavy selector with `EFFIGY_CALLER=<CALLER> effigy
  --host-run-request-id <UUID> <SELECTOR>` to persist its request identity.
  Recover it with `effigy tasks request status --caller <CALLER> --request-id
  <UUID> --json` or `effigy tasks request follow --caller <CALLER> --request-id
  <UUID> --json`. See [guide 080](080-host-wide-validation-admission.md).
- Managed host listeners with readiness, routes and dependencies under
  `[containers.<name>.host_processes]`.
- `effigy gateway setup-tls|up --private-state-root <DIR>`: disposable,
  unprivileged gateway instances.

## Not supported for general use

`effigy gateway setup-listener-handoff`, `listener-handoff-status` and
`remove-listener-handoff`, and the user-owned gateway migration gate, are
source-level groundwork. They install and change nothing, and their live
administrator activation is not qualified. Keep the default root-owned gateway.

## DecodeLabs legacy sites

For a site using `decodelabs-effigy-bundle` (cbs, jal-accounts and similar):

1. Update the catalog pack as above if one is active.
2. Upgrade Effigy, then run `effigy container up --detach`. Adoption requires
   the identity and checkout ownership evidence described above. If that proof
   is unavailable, verify the stack belongs to this checkout, then run
   `effigy container down` followed by `effigy container up --detach`.
3. `effigy doctor` should report no errors. Earlier releases flagged
   `{ task = "defer …" }` references and `[isolation]`/`[state]` tables
   incorrectly.
