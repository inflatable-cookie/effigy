# 085 - v0.15.0 Consumer Migration

This checklist is for consumers moving from v0.14.1 to v0.15.0. Most projects
need no manifest change. Check the rows below that match what your project
uses. The [release contract](../knowledge/contracts/release.md)
owns release authorization; the linked contracts own the behavior described here.

## Host ports, service restarts and data

Three v0.15 defaults change what a consumer sees on a running stack.

- **Published host ports come from the OS or from Compose.** A generated
  service publishes `127.0.0.1::<container-port>`, so the host port is assigned
  when the container starts and can differ after the next `up`, a recreate or a
  VM restart. `up` reads the assigned port back into the route, and nothing is
  reserved across runs. A host port you pinned (`[containers.<NAME>.host].ports`)
  is still used as written, and a collision fails naming the process that holds
  it. A database client, bookmark, `.env` value or editor connection that
  hardcodes a generated port breaks on that move: read the current port from
  `effigy container <NAME> hosts --json` or `effigy container <NAME> status`,
  pin the port in `[containers.<NAME>.host].ports`, or opt into
  `[containers.<NAME>.host].stable_ports = true`, which derives one host port
  per published container port from the checkout path and never records or
  probes it. See [guide 063](063-container-system-guide.md#host-ports).
- **A stopped service comes back by itself.** When a stack declares no policy,
  `up` asks the runtime for `restart: unless-stopped` once the stack is
  running, so a service that stops during a Colima restart, a VM restart or a
  crash returns without a manual `up`. A declared `restart:` (`no`, `always`,
  `on-failure`, …) always wins, so a one-off job that declares `restart: "no"`
  stays down. The rendered Compose file names no restart policy; the runtime is
  updated after the stack starts.
- **`container retire` deletes data unless you say otherwise.** It removes every
  labelled container, network and named volume the checkout owns.
  `effigy container retire --keep-data` keeps the named volumes and lists the
  ones kept. A script that used `retire` as a cleanup step now loses the stack's
  data; add `--keep-data` where the data matters.

`effigy container <NAME> restart <process> [<process>...]` restarts only the
named host processes (and the processes that `depends_on` them, in dependency
order). Containers and the other host processes keep running. A restarted
listener keeps the address it published, whether it declared a fixed port or
asked for one with `bind = "127.0.0.1:0"`, so a dependent's `internal_url`
still resolves. See
[guide 063](063-container-system-guide.md#restart-one-host-process).

A catalog service that `build`s from a Dockerfile gets that Dockerfile as
`dockerfile_inline`, with every `$` doubled so Compose interpolation leaves the
Dockerfile's own `${…}` and `$VAR` intact for the shell inside the image. This
is what makes a catalog `build:` service work on both backends; nothing in your
manifest changes.

A shared backing service's connection environment reaches only the services
that are its clients, which resolve it through `host.docker.internal`. A local
service that used to read a shared service's host and port variables no longer
receives them; declare the values the service needs in its own `env`.

`effigy container data seed` and `data dump` now reach a service declared
`shared = true` instead of failing against the checkout-local stack that does
not carry it: the command uses the shared service's own machine-wide Compose
project and render, so the `stack` and `hybrid` declarations of one shared
identity feed one database and volume. See
[guide 063](063-container-system-guide.md#shared-database-targets).

## Runtime state

Short local foreground tasks keep runtime records in memory. Completed foreground
runs retain no outcome or logs; task status reports `not-recorded`. Use `--run-id`
when a task needs retained run control. Managed runs, QA groups, containers and
environments retain their state in that checkout’s gitignored `.effigy/state/`.
Linked worktrees do not share a journal with their primary checkout.

Only endpoint/route, port and admission facts use `~/.effigy/state/machine.db`.
Nothing is imported from an earlier release, so an upgrade from v0.14.1 needs
no migration step and no command. A 2026-10-27 live proof of a **local** catalog
`mariadb` stack found that the first `up` reconciles a running v0.14.1 stack
through the ordinary apply: the service is recreated once onto the same named
volume and its rows read back unchanged, and a further `up` changes nothing.
Shared-service continuity is unproven and tracked separately. See
[Upgrading from v0.14.1](#upgrading-from-v0141) and
[contract 052 §11](../knowledge/contracts/052-runtime-kernel-contract.md#11-legacy-state).

An unreleased Effigy main build between 2026-10-18 and #276 wrote a central
`~/.effigy/state/kernel.db`; no released version did. Effigy v0.15 has no
importer for it. The file, any cutover manifest and any old per-checkout import
record are ignored: they are never read on a durable open, never changed and
never deleted, and they never refuse a run.

### State capture artefacts moved out of `.effigy/state/`

`.effigy/state/` is the kernel's private checkout root: it must be a 0700
directory, and anything else there is refused. Up to v0.14 the `effigy state`
surface wrote its own files into it — `capture-context/<stack>/<key>.json` and
`apply-context/<stack>/<layer>.json` — with the process umask, so a state run
could leave the root at 0755 and make the whole checkout's runtime state
unreadable.

Those files now live under `.effigy/state-captures/`. For one release:

- If a checkout's `.effigy/state/` still carries that v0.14 mode, the next
  Effigy effect in that checkout tightens it to 0700 and keeps everything in
  it. That includes an ordinary foreground task and a retained (`--run-id`)
  run. Reads never repair it, and it stays untrusted for observations — and for
  a foreign checkout's records — until then.

Move any capture payloads you keep inside `.effigy/state/captures/` (a v0.14
example path) to `.effigy/state-captures/captures/` and update the `source` in
`[state.<env>.captures.*]`; the old context files can be deleted.

Retire a worktree before deleting it when possible. After deletion, run
`effigy container retire --dead --yes` from a live checkout (or supply `--repo`).
It finds each dead stack by the backend's own labels, preserves persistent data
and groups it cannot blame on a missing path, and does not depend on a central
checkout index or a local scope record. `effigy container retire --keep-data`
keeps the named volumes and lists the ones kept.

## Service catalog: packs retired, sources added

The catalog-pack runtime is retired. `effigy service pack` commands now refuse
with the replacement, and the workspace no longer receives a pack from the
host. Installed pack state in `~/.effigy/catalog-packs/` (host or guest) is
ignored with a notice and left untouched; delete it when convenient.

Pack v1.2.0 added `silo`; it otherwise matches an earlier compiled baseline.
The 0.15.0 baseline goes one step further and drops `minio` (below), so a
project that resolved `minio` from either the pack or the baseline must move to
`silo`. To add or change services without an Effigy release, use a
catalog source: the project's `infra/dev/catalog/`, a bundle's `catalog/`, or
a declared `[catalog.sources.<name>]` prepared by the next `effigy dev`,
`effigy bootstrap` or `effigy container up` (or pinned on demand by
`effigy bundle sync`). See
[guide 067](067-catalog-services-reference.md#catalog-sources).

The built-in baseline `minio` catalog service is retired. A manifest whose
`catalog = "minio"` would fall back to it (unqualified with no project, bundle
or declared-source definition, or an explicit `baseline/minio`) fails with a
refusal that names `silo`, and the name is never silently remapped. A `minio`
fragment your own project catalog, bundle or declared source defines still
resolves from that source under Q-005 precedence. For object storage Effigy
ships, move each service to `catalog = "silo"`, which keeps the same S3 API
port `9000`, console `9001`,
`MINIO_ROOT_*` credentials (`minioadmin` defaults), persistent `/data` volume
and `mc ready local` health check. Rename routes and tasks that named the old
service (for example `minio.<host>` or a `minio:reconcile` task). Existing
volumes and their data are untouched: Effigy performs no data migration. See
[guide 067](067-catalog-services-reference.md#retired-catalog-services).

Remove `release.sync-catalog-pack-support-policy` from `[release]` if present;
it is now a manifest error.

## Bundles: `dev`, `bootstrap` and `container up` update a stale source

A bundle or catalog source that is behind updates itself on the next
`effigy dev`, `effigy bootstrap` or `effigy container up`. That includes a local
`base = { type = "path", dir = "..." }` bundle: editing its files is enough.
Switching `[bundle].base`, moving a branch upstream or editing a path bundle
prints one line per source (`bundle updated <old> → <new> (content changed)`)
and the command continues on the new bytes.

`effigy bundle sync` stays as the explicit command. A source declared
`update = "manual"` - in `[bundle]`, or in one `[catalog.sources.<name>]` - is
only moved by `bundle sync`, which is the strict-reproducibility choice. Read
paths still never fetch: when a source is behind they name both sides with
their kind and say the next `dev` or `container up` will update it. A locked
Git pin and the bounded known-version hint are different kinds of identifier,
so the line reads `locked revision 544c0cc9, available digest 2750ab75` rather
than presenting two unlabelled short ids as comparable.
See [guide 066](066-local-manifest-bundles.md) and
[contract 020](../knowledge/contracts/020-remote-bundle-sources-git-and-oci-delivery-contract.md).

## Docs checks resolve explicit paths from the task cwd

`docs check` with no path arguments still checks `README.md` and `docs/` at the
repository root. An explicit path argument now resolves against the invoking
task's cwd, so a nested `docs/effigy.toml` catalog can run
`docs check links README.md knowledge/README.md` and check its own files. The
report prints the resolved set, and `{repo}`/`{cwd}` expand inside
`{ task = "docs check ..." }` references. `{repo}` is the selected catalog
root (the task's cwd), so `{ task = "docs check links {repo}/README.md" }` is
cwd-proof.

For one release, a catalog that already spells arguments from the repository
root (`docs/README.md` while its cwd is `docs/`) keeps passing: when the
cwd-relative path is missing and the root-relative path exists, the check uses
the root path and warns with the `{repo}` spelling. Re-spell those arguments
during this release. See
[guide 029](029-docs-qa-checklist-and-validation.md).

## `skill run --repo` accepts a bare target root

`effigy skill run ... --repo <DIR>` no longer requires the target directory to
carry a repository marker. An explicit bare fixture target runs the installed
skill task with that directory as its cwd, and the JSON evidence reports
canonical root paths (so a symlinked spelling such as `/var` against
`/private/var` compares equal). Discovery without `--repo` still requires a
resolvable consumer root; see
[guide 047](047-agent-and-cross-repo-adoption.md).

## Removed surfaces

- `effigy release simulate` is retired. Use `effigy release --plan`, which shows
  the whole release pipeline with no mutation: every identity's current and next
  version and tag, the files to change, gates by stage, artifacts, targets and
  approval checkpoints. `release --plan --version <SEMVER>` covers the old
  `simulate --version`. Today's `[release]` table is unchanged, so the shorthand
  keeps one identity, one `tag` target and gates in `certify`; named
  `[release.identities]`, `[release.targets]`, `[release.artifacts]`, gate
  `stage` and `approve` are new. `effigy release run` replaces `release
  prepare` and `release execute`; an existing shorthand `[release]` runs
  unchanged through it, and `release receipt` prints what the Run recorded. See
  [guide 051](051-release-orchestration.md) and
  [contract 054](../knowledge/contracts/054-release-platform-contract.md).
- `effigy system` is retired. Replace `effigy system up|down|status|logs` with
  `effigy container up|down|status|logs`: without a name it resolves
  `[containers].default` and then the `[systems].default` workspace container,
  and `--system <NAME>` selects one declared system. Replace
  `effigy system repair` and `effigy system reset-runtime` with
  `effigy container profile repair` and `effigy container profile reset-runtime`;
  both keep their refusals, accept `--repo` and `--system`, and keep the
  `effigy.system.recover.v1` JSON envelope. `[systems]`, `effigy workspace` and
  `effigy exec` are unchanged. Rhai scripts that called `system::status` or
  `system::logs` have no replacement function; call a task that runs
  `effigy container` instead. See [guide 064](064-system-workspace-and-dev-contract.md).
- The code graph is gone (Q-009): `effigy graph`, `effigy docs context`, the
  `effigy-codegraph` crate and its SQLite index. Use `rg` for code navigation,
  `docs/README.md` for the documentation index, and `effigy test --plan` to
  choose tests; `docs check` is unchanged. Delete `scan boundary-violations`,
  `scan dead-code`, `scan validation-gaps`, `scan --graph-context`,
  `scan --path` and `scan --stdin` from scripts and CI, and remove the
  `[scan.boundary_violations]`, `[scan.dead_code]`, `[scan.validation_gaps]`
  and `[catalog.graph]` tables: for the whole v0.15 line each still loads and
  is ignored, named in the one deprecation notice per manifest, because
  ignoring it changes nothing else. Delete them when convenient. The remaining
  scanners work without graph enrichment. An existing `.effigy/graph/`
  directory is repository-local state that Effigy ignores and never removes;
  delete it by hand if the disk space matters. `[docs_policy.graph]` and
  `[docs_policy.sources]` are still accepted but nothing reads them.
- Replace `effigy watch` with your tool's native watch option or explicit task runs.
- Replace `effigy tasks migrate` with explicit task and test-suite definitions;
  inspect `effigy config` for examples.
- Unset `EFFIGY_MANAGED_STREAM` and use `--headless`. A set variable now errors
  before managed children launch, including with `--headless` already present.
- Remove `[manifest].root`; it now reports a source-specific error.
- Move fragments from `~/.effigy/catalog/` to each repository's
  `infra/dev/catalog/`. The old directory is ignored with a warning and preserved.
- The built-in baseline `minio` catalog service is removed. Change
  `catalog = "minio"` to `catalog = "silo"` and rename the service's routes and
  tasks; the refusal names `silo` and nothing is remapped. A `minio` fragment
  your own project catalog, bundle or declared source defines still resolves
  from that source. Existing data volumes stay as they are. See
  [Service catalog: packs retired, sources added](#service-catalog-packs-retired-sources-added).
- `effigy gateway recover` is retired. v0.14.1 identity-bearing gateway upgrades
  retain `gateway up`/`down`. Pre-0.14 numeric-only state requires administrator
  migration as described in [architecture 034](../knowledge/architecture/034-gateway-legacy-upgrade-recovery.md).
- Run docs QA selectors directly instead of `docs qualified`. The private
  assurance recipe and build profile are removed.
- Listener transition receipts are no longer read or written; existing files
  stay untouched. Current listener state and diagnostics remain available.
- `[drafts]`, `draft` step keys, QA member `surface = "draft"`, `effigy draft`
  and `effigy drafts` are removed. Move each definition to
  `[tasks.<name>]` with `visibility = "internal"`, replace `draft` steps with
  `task = "<name>"`, and run the task by name. The manifest error names the
  replacement; see [contract 046](../knowledge/contracts/046-published-and-draft-task-surface-contract.md).
- `[shell]` is removed. Managed shell tabs always run
  `exec ${SHELL:-/bin/zsh} -i`; delete the table. A manifest that still
  declares it loads, and the table is ignored with the one-notice-per-manifest
  deprecation.
- Five scanners are removed (Q-009): `scan attention-markers`,
  `scan comment-ratio`, `scan generated-assets`, `scan generated-in-src` and
  `scan stale-suppressions`. Each refuses with its replacement (or says there
  is none). The `[scan.attention_markers]`, `[scan.comment_ratio]`,
  `[scan.generated_assets]`, `[scan.generated_in_src]` and
  `[scan.stale_suppressions]` tables keep loading and are ignored, named in the
  one deprecation notice per manifest, because ignoring them changes nothing
  else. Delete them when convenient. For
  TODO/FIXME searches use `rg -n 'TODO|FIXME' <path>`; keep bulky generated
  output out of versioned paths with `.gitignore`. The `scan.comment_ratio`,
  `scan.generated_assets`, `scan.generated_in_src`, `scan.attention_markers`
  and `scan.stale_suppressions` Rhai host features are gone too.
- `effigy artifact` is removed. Insert `state` after `effigy`, so
  `effigy artifact inspect <REF|PATH>` becomes
  `effigy state artifact inspect <REF|PATH>` and the same holds for `stage` and
  `capture`. Flags, behaviour and the `effigy.artifact.*.v1` payloads are
  unchanged, and layered captures stay on `effigy state capture`. A Rhai script
  that calls `artifact::inspect`, `artifact::stage` or `artifact::capture` now
  calls `state::artifact_inspect`, `state::artifact_stage` or
  `state::artifact_capture`, with the same arguments and option maps. The old
  spelling fails with this replacement. See
  [guide 072](072-artifact-commands-guide.md).
- `effigy gateway setup-listener-handoff`, `listener-handoff-status` and
  `remove-listener-handoff` are retired with the experimental listener handoff.
  There is no replacement: the gateway runs as your user, so use
  `effigy gateway up` and inspect it with `effigy gateway status`.
- `[demos]` and `effigy demo` are removed; every demo converts to an ordinary
  task. The registry, receipts, retained history and browser no longer exist,
  the `demo.*` Rhai host features are gone, and `effigy config --target demos`
  no longer exists. Each `[demos.<name>]` becomes `[tasks."demo:<name>"]` with
  the same `run`, `title` and `summary` merged into the task `description`
  ([guide 022](022-manifest-cookbook.md#task-descriptions)), and
  `group = "Demos"` to keep them grouped:

  ```toml
  # Before
  [demos.checkout]
  title = "Checkout"
  summary = "Add an item and pay"
  run = "bun run demo:checkout"

  # After
  [tasks."demo:checkout"]
  description = "Checkout — Add an item and pay"
  run = "bun run demo:checkout"
  group = "Demos" # optional; v0.14.1 rejects `group` and `description`
  ```

  Demo-only metadata (`proof`, `owner`, `mode`, `status`, `covers`, `tags`,
  `artifacts`, `receipt`) has no task equivalent; drop it. Historical
  `.effigy/demo/` state and a consumer's own `demos/` script directory are
  untouched. A `[demos]` table keeps loading and is ignored, with this same
  recipe in the one deprecation notice per manifest; `effigy demo` and
  `effigy config --target demos` still refuse with it.
- Rebuild `[bootstrap]` around ordinary task selectors and pinned sources
  (Q-009, [guide 057](057-bootstrap-repo-bringup.md)):
  - `run` (and the `setup` alias for it) is now `setup`, an ordered list of
    plain task selectors. Move any inline run steps into the task the list
    selects.
  - `start` takes one selector. Sequence multiple steps inside a task.
  - `submodules = "recursive"` (or `"none"`/`"init"`) becomes
    `submodules = true`, or is deleted when the repo has no submodules.
  - `[[bootstrap.children]]` becomes a pinned `[sources.<name>]` table with
    `git`, `rev` (or `rev_file`) and `path`. Delete
    `effigy bootstrap children status|sync` from scripts; use `effigy doctor`
    for source drift.
  - `effigy bootstrap deps sync` is gone: make dependency preparation an
    ordinary task selected by `setup` (a lock refresh is a deliberate repo
    task, not a flag).
  - `--db-seed`, the OCI/file dump prompts and the `bootstrap:db-seed` fallback
    are gone: a first seed is a repo task in `setup`, and
    `effigy container data seed` imports a user-supplied dump explicitly.
  - `--fresh` and `effigy bootstrap teardown` are gone: environments own reset,
    so stop one with `effigy container <name> down`.
  - `--backend` is gone: the declared environment and the machine backend
    preference choose the backend.
  - `--start` is gone because start is the default; keep `--no-start`.
  - A non-empty destination or a pinned source with local changes is now
    reported as drift or refused rather than prompted for. Bootstrap never
    resets a working copy.

- `effigy contracts validate-selection` is folded into `check-json`. Use
  `effigy contracts check-json --validate-selection` for this run's payload
  (already implied by `--print-selected=json`), or
  `effigy contracts check-json --validate-selection --artifact <PATH>` for a
  stored artifact. The command refuses with this replacement.
- `effigy contracts check-json` no longer assumes Effigy's documentation paths.
  Declare your own under `[contracts]` in `effigy.toml`:

  ```toml
  [contracts]
  schema_index = "docs/knowledge/contracts/json-schema-index.json"
  selection_contract = "docs/knowledge/contracts/json-selection-contract.json"
  ```

  A project that declares neither is refused with `no JSON schema index
  configured`. `--index` and `--contract` still override the configured paths.
  If you validate command payloads beyond schema/schema_version identity, add a
  `payload_schemas` map to your index (schema id → Draft 2020-12 document,
  relative to the index file); see
  [contract 055](../knowledge/contracts/055-project-json-contract-validation-contract.md).

### `[bootstrap]` keeps loading in v0.15

A v0.14.1 manifest still loads: retiring the keys above is a migration, not a
parse error. For the whole v0.15 line Effigy reads the retired `[bootstrap]`
spellings and prints one deprecation notice per manifest. It reaches stderr
once per checkout per manifest digest, `effigy doctor` names it on every run,
and a nested Effigy invocation (a task that runs `effigy`) stays quiet because
its parent already said it. `--json` never writes it to stderr: it reports it
in the envelope's `warnings`.

- `[bootstrap].run` is read as `setup`. `{ task = "..." }` entries become
  selector strings, and inline `run`/`rhai`/command steps are added as internal
  tasks that `setup` selects in the same order, so they stay runnable.
- `{ task = "..." }` entries in `setup` are read as `"..."` selectors.
- `submodules = "recursive"`/`"init"` is read as `submodules = true`, and
  `"none"` as `false`.
- a multi-selector `start` chain runs as one internal task.
- `[bootstrap].children` (from the project or from a bundle through
  `[manifest].extend`) and the retired `bootstrap:db-seed` callback keep the
  manifest loadable, but `effigy bootstrap` refuses them with the migration
  message: pinned sources, a first-seed task in `setup`, and a repo-owned
  dependency task replace them.
- a `run`/`setup` entry that still invokes `bootstrap deps sync`,
  `bootstrap children status|sync` or `bootstrap teardown` also loads, and
  `effigy bootstrap` refuses it with that subcommand's replacement.

The sections for features v0.15 removed keep loading for the same release when
ignoring them changes nothing else: every removed scanner's `[scan.<name>]`
table, `[catalog.graph]`, `[demos]` and `[shell]` are ignored and named in
that same notice ([guide 022](022-manifest-cookbook.md#removed-sections)).
`[drafts]` and `draft` step references are not in this group: they stay
manifest errors, because ignoring them would silently drop task definitions.

Update the manifest to the shapes above. The translation is removed after
v0.15, when these keys become manifest errors again.

Two more spellings still load for this release and are removed in v0.16, so
re-spell them now rather than after the next break: a manual
`[manifest].include` `optional` or `override`, and the kebab-case keys
`[contracts].schema-index`, `[contracts].selection-contract` and
`[sources.<name>].rev-file`. Omit a missing include or use auto-discovered
`effigy.local.toml` instead of `optional`; use `effigy.local.toml` or
`[manifest].extend` instead of `override`; write `schema_index`,
`selection_contract` and `rev_file`. One notice per manifest names the
replacement, `effigy doctor` reports it, and `--json` carries it in `warnings`.
See [guide 070](070-per-machine-overlays-and-external-mounts.md).

Delete `identity`, `unlock` and `external` declarations under `[secrets.vault]`.
They are retired after consumer cleanup; the error names the file and line.
These keys only restated the passphrase default. Vault paths, stored values
and runtime unlocks keep their existing behavior. A retired key inside a bundle
export names the export file and line too: refresh a pinned or cached bundle
with `effigy bundle sync`, or delete the line when you own that bundle.

## Behavior changes

| If you rely on… | What changes |
| --- | --- |
| `deploy apply` or `deploy redeploy` | Both refuse as not yet supported, including with `--yes`, and name the unexecuted obligations. Model/export and environment configuration stay compatible; old reports remain readable. Use model/export while full execution is designed in the deploy lane. See [guide 074](074-deployment-guide.md). |
| Detached stacks (`startup = "detached"`, e.g. the DecodeLabs bundle) | A detached `up` reads the project inventory including stopped siblings and does not refuse a complete stack whose inputs changed or that predates the admission record: one apply converges it. A container whose Compose project or Effigy checkout and scope labels name another owner is not this checkout's. A container from an earlier release that carries no Effigy checkout label is reported, never adopted: retirement lists it under `kept`, and `effigy container down` followed by `effigy container up --detach` relabels the stack. Editing the manifest of a running stack and running `up --detach` applies the change, and a failed or interrupted `up` leaves nothing to clean up because the next `up` reconciles from what is running. See [contract 005](../knowledge/contracts/005-container-runtime-contract.md). |
| A shared service whose render directory was deleted (under `~/.effigy/shared-services/`) while a container created from that render, or from an older one, still exists, running or stopped | `container up` no longer restores the render silently or starts the container against a missing bind source. It refuses before publishing, stopping, removing or starting anything, and names the container. The container and its named data volume are unchanged. Recover by removing exactly that container with the runtime's `rm -f <name>` (`docker rm -f` or `nerdctl rm -f`; the named volume stays), then run `effigy container <NAME> up`, which re-renders the shared service and creates it on the preserved volume. A container whose render is present and differs from the current one is replaced as before, and a missing render with no container takes the normal creation path. See [contract 005](../knowledge/contracts/005-container-runtime-contract.md). |
| Direct `compose_file` containers | `compose_file` is deprecated and read as project catalog fragments for one release, with a warning. Run `effigy container migrate <NAME>` to write `infra/dev/catalog/<container>-<service>/` and replace the key; the render does not change. Compose features a fragment cannot express refuse with the key to move. Named volumes become `<project>-<volume>`; old `<project>_<volume>` volumes are left alone. ## New, opt-in

- `data_from` on `[containers.<env>]`: borrow another environment's service
  data volumes, so a container environment and its bundle-hybrid twin see one
  database and one bucket per checkout and switching between them hands the
  data over automatically. See [guide 063](063-container-system-guide.md).
- `effigy container <NAME> shell --command … --bounded`: deadline- and
  byte-bounded finite commands with the `effigy.container.bounded-exec.v1`
  payload.
- `EFFIGY_ADMISSION_HOOK`: gate `admission = "heavy"` tasks with your own
  command, held for the whole run. `effigy --run-id <key> <task>`,
  `effigy runs` and `effigy run status|logs|stop <run>`: name, inspect, follow
  and stop any run. See [guide 080](080-host-wide-validation-admission.md).
- Managed host listeners with readiness, routes and dependencies under
  `[containers.<name>.host_processes]`.
- `effigy gateway setup-tls|up --private-state-root <DIR>`: disposable,
  unprivileged gateway instances.
- `effigy fmt rust <FILE>...`: format an explicit Rust file set with rustfmt
  and the config nearest each file. `--check` reports without writing. Use it
  where `cargo fmt` would follow a path-linked workspace into unrelated crates.
  Relative paths are cwd-relative, and a repository `fmt` task keeps that word
  for itself — `effigy fmt-rust <FILE>...` is the built-in's explicit spelling
  when it does. See [guide 025](025-command-reference-matrix.md) and
  [task routing precedence](016-task-routing-precedence.md).

## Upgrading from v0.14.1

Proven on 2026-10-27 by an owner-side live proof at head `16cee887`, using the
released v0.14.1 binary and this branch on a disposable fixture with one
**local** catalog `mariadb` service and a unique project name. It established
local named-volume and row continuity two ways: v0.14.1 `down` and then this
branch's `up`, and this branch's `up` over the still-running v0.14.1 stack. In
both the service was recreated onto the same `<project>-<service>-data` volume
and the sentinel row read back unchanged, and one further `up` was idempotent.

It proved nothing about shared services. A v0.14.1 shared MariaDB fails during
initialisation on this fixture shape, so shared-volume continuity stays
unproven and is tracked as separate Queue lead `44b83952`. Do not read the
local result as an assurance for a stack's shared database.

The steps below describe the proven local-service path only. They are guidance
for when v0.15 qualifies for release; they are not a release or install
instruction, and they carry no assurance about shared services.

1. Stop nothing by hand. Keep the data: do not delete named volumes, and do not
   run `effigy container down --keep-data`-style cleanup on the old install.
2. Run `effigy container up --detach` with v0.15 (or start a task that brings
   the stack up). The first apply reconciles the running stack; a local catalog
   service is recreated once because its labels and render changed, and it
   attaches the same `<project>-<service>-data` volume.
3. Check the data: `effigy container <NAME> shell` then query the database, or
   compare what your app reads. A local service's named volume is not recreated
   or renamed by the upgrade.
4. If you prefer a clean stop first, running v0.14.1's `effigy container down`
   before the upgrade keeps the volumes and makes the first v0.15 `up` a fresh
   create. Both orders kept the local row in the proof.

Leftover v0.14.1 lifecycle markers and leases are ignored; delete them once
every stack has been brought up by v0.15.

## DecodeLabs legacy sites

For a site using `decodelabs-effigy-bundle` (cbs, jal-accounts and similar):

1. Upgrade Effigy, then run `effigy container up --detach`. Adoption requires
   the identity and checkout ownership evidence described above. If that proof
   is unavailable, verify the stack belongs to this checkout, then run
   `effigy container down` followed by `effigy container up --detach`.
2. `effigy doctor` should report no errors. Earlier releases flagged
   `{ task = "defer …" }` references and `[isolation]`/`[state]` tables
   incorrectly.
